# Report export — build spec

The in-app **Export report** feature produces a professional network assessment
report (print-to-PDF from the browser). This is the binding spec; it merges WLAN
site-survey, OWASP/PTES pentest-report, and Mist/Meraki health-dashboard
conventions (researched July 2026). Two hard rules override everything: **no
false data** (every number traces to a real repository query) and **no slop**
(refined-prose; no chart junk; the anti-patterns below are failures).

## Structure (section order)

1. **Cover** — title, site/network name, date, data window, "generated by
   UnifiOptimizer", a confidentiality line.
2. **Executive summary** (fits one page) — a one-sentence posture verdict; the
   scorecard (overall health score + findings-by-severity counts in CVSS colors);
   the top 3–5 findings in plain business language (user experience, not dBm);
   a prioritized one-line recommendation summary. No jargon.
3. **Scope & methodology** — what was assessed, the data source (controller
   telemetry + local probes), sampling cadence, the collection window, and the
   honest limitations (no spectrum analyzer, no client-side RSSI, gateway-less
   WAN measured by probe, etc.). Methodology up front = credibility.
4. **Network inventory** — count tiles (APs, switches, gateway, clients) + a
   device table (name, model, role, uplink).
5. **Topology** — layered diagram (internet → gateway → switches → APs → mesh →
   clients), one visual language, mesh links labelled with RSSI and coloured by
   backhaul health.
6. **Health & performance** — the SLE scorecard tiles + a health trend line over
   the window; per-SLE scores (coverage, capacity, connect, roaming, WAN, infra)
   with the top offenders each.
7. **RF environment** — channel-utilisation bars per band (70% reference line),
   neighbour/rogue-AP density by channel (the environmental context), honestly
   framed (a rural RF-dense site is context, not 80 alarms).
8. **Client analysis** — RSSI distribution histogram (colour the weak tail),
   clients-per-AP load bars, and a worst-devices (top-offenders) table.
9. **Detailed findings** — a summary table first (ID, title, severity, affected),
   then per-finding entries using the FIXED template below.
10. **Recommendations / roadmap** — ranked by severity, phased (now / soon /
    strategic), each traceable to a finding ID, each SPECIFIC and actionable.
11. **Appendix** — severity rubric, thresholds used, full inventory, methodology
    detail, glossary.

## The findings template (every finding, identical shape)

`ID` (stable, e.g. WLAN-03) · `Severity` (Critical/High/Medium/Low/Info, CVSS
colours) · `Affected assets` · `Observation` (the measured fact + its chart/evidence)
· `Impact` (user-experience terms) · `Root cause` · `Recommendation` (specific,
ordered). A finding without a concrete, specific recommendation is not done.

Map netadmin's real data to it: Observation = the detector's evidence numbers;
Impact = the SLE fail-minutes / affected clients; Root cause = the detector's
playbook + any correlation incident; Recommendation = the fix template or the
advisory. Group correlated issues (incidents) so a root cause and its symptoms
read as one finding.

## Charts (Tufte-clean; hand-rolled SVG, no chart lib, no matplotlib in runtime)

Reuse the frontend's existing SVG chart primitives where possible. One idea per
chart, recessive grid, direct labels, one accent + the status ramp, no gridline
walls, no 3-D, no gradients, no dual axes. Minimum set: health trend line;
per-SLE score bars; mesh-uplink-RSSI trend (the key evidence); client-RSSI
histogram (weak tail coloured); channel-utilisation bars by band; neighbour
density by channel; clients-per-AP bars; worst-devices table.

## Severity colours (CVSS-aligned, one system end to end)

Critical = deep red (`#d70015`), High = orange (`#b25000`), Medium = amber,
Low = green (`#1e7a34`), Info = grey. The same chip colour in the scorecard, the
findings table, and any per-entity status. Map netadmin P1→Critical/High,
P2→High/Medium, P3→Low, per the SLE impact.

## Honesty conventions

State the data window and sampling. State limitations plainly up front. Never
show an average without its distribution (histogram, not just a mean). Frame
severity as an input to the reader's decisions, not a verdict. Neighbour-AP
noise is environmental context, aggregated — never 80 individual "issues."

## Anti-patterns (slop firewall — any of these is a failure)

Bare table dump with no narrative or prioritisation · chart junk (3-D, shadows,
rainbow, gridline walls) · green-everything · mixed topology icons / spaghetti ·
purple-pink gradients, ✨ headers, decorative accent italics · prose tells
("comprehensive", "leverage", "robust", "seamless", em-dash overuse, sycophantic
openers, the reflexive 5-bullet list) · vague non-actionable recommendations ·
averages hiding the bad corner.

## Delivery

A `/report` (or `/reports`) surface renders the report print-optimised; an
**Export report** action opens it and triggers the browser's Save-as-PDF (no
server-side PDF engine, keeping the daemon dependency-light). Data comes from a
backend report assembler that returns the full report model (scorecard, sections,
findings in the template shape, chart series, topology) from real repository
queries — the frontend renders, never fabricates.
